# VPSPilot — Rust-First Backend Migration Plan

Status: proposal. Based on a **static, read-only audit** of the repository at branch
`chore/changelog-v0.2.0` (commit `0a15888`). No code was changed. Tests were **not run** and the
app was **not launched** for this audit; every "by reading" statement below should be confirmed
by the acceptance criteria of the milestone that depends on it.

> **Update (2026-11-24): F1, F7 and M0 are done.** The History permission defect was reproduced in
> the real app (`... not allowed. Command not found`) and fixed in PR #11, which also added
> `src-tauri/tests/acl_consistency.rs` and a CI check that generated permission files are
> committed. The text below is the original audit and is kept as written; it still describes F1
> and M0 as open. F2-F6, F8 and milestones M1-M6 remain proposals.

## 1. Executive summary

**The backend is already Rust.** SSH, host-key trust, credentials, terminal sessions, monitoring,
alert evaluation, history storage and aggregation, Docker parsing and request validation, retention
and every SQLite write are implemented and enforced in `apps/desktop/src-tauri/src` (about 9,700
lines including tests). The TypeScript layer is a presentation layer plus thin IPC wrappers. There is
no business rule that exists *only* in TypeScript.

So this is **not a rewrite and not a large migration**. The audit found:

| # | Finding | Kind | Severity |
| --- | --- | --- | --- |
| F1 | `get_metric_history`, `get_history_retention_days`, `set_history_retention_days` are registered in `generate_handler!` but missing from `build.rs` `COMMANDS`, the capability file and `permissions/autogenerated/`. Tauri 2.12.5 rejects any app command that has no matching permission once an app manifest is defined (`tauri-2.12.5/src/webview/mod.rs`, ACL check around lines 2065-2105). **The History tab and the retention setting very likely fail in the real app.** Playwright cannot catch this because `e2e/tauriMock.ts` replaces IPC. | Defect | **P1** (confirm first) |
| F2 | Adding or editing a server is two IPC calls orchestrated by React (`ServersPage.save`: `add/update_server`, then `set_server_credential`). A failure in the second leaves a saved profile and a "saved, but credential could not be updated" notice. | Orchestration in UI | P2 |
| F3 | The monitor forwarder (alert evaluation, gap handling, history recording, alert closing, registry cleanup, about 150 lines) lives in `commands/monitor.rs`, a Tauri command file. Only `is_gap` and `validate_interval` are tested. `alerts_for_sample` also does SQLite I/O on an async worker, while history writes correctly use `spawn_blocking`. | Rule placement | P2 |
| F4 | The "revoke terminals/monitor when identity changed" policy is an inline closure in `commands/servers.rs::update_server`, not in `servers::service`. | Rule placement | P3 |
| F5 | Failures from terminal start, Docker and logs reach the UI as `AppError{code:"connection", message}` with free text. `deriveConnectionStatus` therefore shows a terminal authentication failure as "Connection error", while a monitor authentication failure shows "Authentication failed" (it has `cause`). | Error classification | P3 |
| F6 | Validation rules and limits are mirrored by hand in TypeScript (`serverValidation.ts`, `alertsState.ts`, `historyState.ts`), including a hand-written IPv6 parser. Rust re-validates everything, so this is UX duplication, not a security gap, but it can drift. A concrete drift candidate: TS `IPV4` (`1?\d?\d`) accepts octets with leading zeros such as `01.2.3.4`, while Rust's `IpAddr` parser rejects them and the hostname fallback rejects an all-numeric last label. | Duplication | P3 |
| F7 | No test links `build.rs COMMANDS` ↔ `generate_handler!` ↔ `capabilities/default.json`. Already noted as T-03 in `docs/audits/VPSPilot_Fix_Priority.md`. This is how F1 happened. | Test gap | P1 (with F1) |
| F8 | No test pins the JSON shape of IPC events and results (`Metrics`, `MonitorEvent`, `AlertEvent`, `HistoryRange`, `AppError`) against the TypeScript types that mirror them. | Test gap | P3 |

Recommended path: six small milestones (Section 7), the first of which is a bug fix. No new crate,
no change to the app identifier, SQLite migrations, SSH host-key verification or credential storage.

## 2. Current architecture

```
React (UI + view-models)                       Rust (Tauri 2, single crate `vpspilot`)
-----------------------------                  ------------------------------------------------
pages/, components/        presentation        commands/*        thin Tauri wrappers (+ F3/F4 orchestration)
hooks/ useMonitoring,      UI state holders    servers/ alerts/ history/   model -> repo -> service
       useConnections,                         ssh/ client, hostkey, known_hosts, service,
       useServers, useTheme                         terminal*, monitor/, docker/
services/*State.ts         pure view-models    credentials.rs    CredentialStore trait + Windows impl
services/*Api.ts           typed invoke()      db.rs             migrations (PRAGMA user_version)
services/ipc.ts            error normalizing   state.rs          AppState: db, credentials, registries
types/*.ts                 mirrored DTOs       error.rs          AppError {code, message, field?}
        |  invoke() / Channel                  build.rs + capabilities/ + permissions/   ACL
        +--------------------------------------> 26 commands in COMMANDS, 29 in generate_handler!
```

Properties worth preserving (all confirmed in code):

- **Layering is already right.** `servers`, `alerts`, `history` and `ssh::service` are Tauri-independent
  and unit-tested with in-memory SQLite and a `MemoryStore` credential store.
- **Commands take ids, not connection parameters.** `prepare_connection` reads host, port, user and
  secret inside Rust; the secret never reaches the frontend.
- **Host-key gating is in Rust** (`ssh/client.rs::connect_authenticated`, plus explicit pre-checks in
  `ssh/docker/mod.rs`): nothing is sent to an untrusted host, and a changed key is a hard failure.
- **Alert engine is pure** (`alerts/engine.rs`: no I/O, no clock) and authoritative. The frontend never
  evaluates a threshold.
- **History aggregation is SQL in Rust** (`history/repo.rs::bucketed`); the frontend only draws it.
- **Docker/log requests are validated before any DB or network access** (`LogsRequest::new`).
- **Profile + credential changes** use an ordered take/commit/compensate protocol (`servers/service.rs`).
- **Lock discipline** is documented (DB first, registry second; never across an await).

## 4. Step 3 findings: is Rust authoritative?

| Area | Rust authoritative? | Evidence | Gap |
| --- | --- | --- | --- |
| Server validation | **Yes** | `validate_server_input`, `validate_secret` called in `add_server`/`update_server`/`set_credential` | TS mirror can drift (F6). |
| Connection-status decisions | **Yes for gating and failure cause; no for the merged label** | `connect_authenticated` refuses untrusted hosts; monitor `cause`; `deriveConnectionStatus` only combines two UI-held channels | Terminal/Docker failure has no `cause` (F5). |
| Monitoring state transitions | **Yes** | State machine and retry rules in `ssh/monitor`; TS `applyMonitorEvent` only folds events | None. |
| Alert evaluation | **Yes, exclusively** | `alerts/engine.rs`; no threshold logic in TS | Rule placement of the pipeline (F3). |
| History aggregation | **Yes, exclusively** | `history/repo.rs::bucketed`, `range_stats`, clamps in `history/service.rs::query` | Commands not in ACL (F1). |
| Docker request validation | **Yes, exclusively** | `LogsRequest::new` runs before DB/network; commands are constants | None. |
| Credential handling | **Yes** | secret read only inside `prepare_connection`; write-only `set_server_credential`; compensation protocol | Two-call save (F2). |
| Authorization | **Mostly** | ACL per command; id-only commands; unguessable terminal session ids; trust bound to last observed key | F1/F7. |
| Error classification | **Mostly** | `ConnectionTestOutcome`, `ErrorCode`; Docker outcomes are typed results | Free-text `connection` errors (F5). |

Minor duplicated behaviour that is **benign and should stay**: when a monitor fails or stops, the
frontend drops that server's active alerts (`useMonitoring.applyStatus`) and Rust also emits resolve
events (`close_alerts`). Rust skips the events if the server was just deleted or the monitor was
superseded, so the frontend drop is the only thing that clears the list in those cases.

## 5. Target architecture

Keep the single Tauri crate and the current layering. **Do not add crates**: the service modules are
already Tauri-independent, test time is short, and there is no second consumer (no CLI, no agent, no
HTTP backend). Revisit a split only if a headless consumer ever appears.

| Layer | Responsibility | Where | Change |
| --- | --- | --- | --- |
| Domain | Validation, alert state machine, retention rules, sampling gate, host-key decision, request validation | `servers/model`, `alerts/{model,engine}`, `history/{model,service}`, `ssh/hostkey`, `ssh/docker/logs` | None. Add `limits.rs` (M4) as the one home for shared constants. |
| Application services | Use-cases and policies; Tauri-free; take `&Connection` and `&dyn CredentialStore` | `servers/service`, `alerts/service`, `history/service`, `ssh/service` | M1 `save_server`; M2 `ChangeEffects`; **new `monitoring/pipeline.rs`** (from `commands/monitor.rs`). |
| Infrastructure adapters | SSH, PTY, remote parsers, SQLite repos, Windows credential store | `ssh/*`, `*/repo.rs`, `credentials.rs`, `db.rs` | None. |
| Tauri IPC | Thin commands + channels; one `allow-*` per command | `commands/*`, `build.rs`, `capabilities/` | M0 fixes ACL; later milestones add commands in all three places. |
| Shared models | `AppError`, `MonitorEvent`, `StreamEvent`, DTOs | `error.rs`, per-module `model.rs` | M3 additive `kind`; M5 golden JSON. |
| Database boundary | Only `*/repo.rs` and `db.rs` touch SQL; one connection behind `AppState::conn()` | unchanged | Existing migrations untouched; no new migration is needed by any milestone. |

**IPC contract rules for every milestone**

1. Changes are additive (new command, new optional field). Existing command names and field names
   keep working until the frontend no longer uses them.
2. A new command is added to `build.rs COMMANDS`, `generate_handler!`, `capabilities/default.json`
   and `permissions/autogenerated/` together; M0's test enforces this.
3. Removing an old command (and its permission) happens only after the frontend stopped calling it.
   That tightens permissions and is optional.
4. Errors keep `{code, message, field?}`; any new field is optional and skipped when absent.

## 6. Test strategy

Existing strengths: per-module Rust unit tests on in-memory SQLite and `MemoryStore`, a local test
SSH server for the SSH, monitor, Docker and terminal suites, Vitest on every `services/*State.ts`, and
Playwright E2E.

Gaps and additions:

| Layer | Addition | Milestone |
| --- | --- | --- |
| ACL | Rust test that parses `build.rs` `COMMANDS`, the `generate_handler!` list and `capabilities/default.json` and asserts all three sets are equal, and that each command has a file in `permissions/autogenerated/`. | M0 |
| Application services | `monitoring::pipeline` tested with fake sinks (sample events, gaps, restart supersede, send failure, DB failure) instead of through a Tauri `AppHandle`. | M2 |
| Policy | Pure `ChangeEffects` tests (rename keeps sessions; host/port/user/auth change revokes). | M2 |
| Error classification | Table test from SSH failure to `kind`, and a Vitest case for terminal `auth_failed` status. | M3 |
| Conformance | One JSON corpus of valid and invalid server and rule inputs, executed by **both** `cargo test` and Vitest. | M4 |
| IPC contract | Golden JSON files for `Metrics`, `MonitorEvent`, `AlertEvent`, `HistoryRange`, `AppError`, `ConnectionTestResult`: Rust serializes and compares, Vitest checks they satisfy the TS types. Evaluate `ts-rs`/`specta` only if hand-maintained goldens prove burdensome. | M5 |
| Real IPC | At least one Playwright/`tauri-driver` smoke path, or a manual checklist item, that exercises the real ACL (the current mock cannot). | M0 |
| Runtime | Windows manual run of the beta checklist (`docs/releases/v0.2.0-beta-checklist.md`) stays the only check against real OpenSSH and Credential Manager. | all |

## 7. Migration roadmap

Order is by value and risk: fix the defect first, then orchestration, then rule placement, then
classification, then drift guards.

### M0 — Register the history commands in the ACL (F1, F7)

1. **Problem.** Three commands are handled but not in the ACL manifest, so the real webview is
   likely denied. Nothing in CI links the three lists.
2. **Files.** `src-tauri/build.rs`, `src-tauri/capabilities/default.json`,
   `src-tauri/permissions/autogenerated/` (3 new TOML files, generated by the build), a new test
   (for example `src-tauri/tests/acl_consistency.rs`).
3. **Rust.** Append the three names to `COMMANDS`; grant `allow-get-metric-history`,
   `allow-get-history-retention-days`, `allow-set-history-retention-days`; add the consistency test.
4. **Frontend.** None.
5. **Tests.** The consistency test (fails today). Manual: run the real app, open Dashboard > History,
   change retention in Settings, confirm both work. Capture the exact denial message in a dev build
   first (`Command get_metric_history not allowed by ACL` or the longer debug form) to confirm F1.
6. **Compatibility.** Adds three explicit grants; no wildcard, no other plugin. This matches the
   documented model ("one `allow-*` per command") and does **not** weaken permissions. No schema or
   credential impact.
7. **Acceptance.** Test green; History tab and retention work in `tauri dev` and in an installed build;
   capability list equals handler list.

### M1 — One `save_server` command (F2)

1. **Problem.** Create/edit plus credential change are two IPC calls driven by the UI; the second can
   fail after the first committed.
2. **Files.** `servers/service.rs`, `servers/model.rs`, `commands/servers.rs`, `lib.rs`, `build.rs`,
   capabilities and permissions, `services/serversApi.ts`, `pages/ServersPage.tsx`, `e2e/tauriMock.ts`.
3. **Rust.** `save_server(id: Option<String>, input, credential: Keep | Set(secret) | Clear)`:
   validate the profile **and** the secret before any write, then reuse the existing take/commit/
   compensate protocol so there is one outcome and one revocation. Keep `add_server`, `update_server`,
   `set_server_credential`, `clear_server_credential` unchanged for now.
4. **Frontend.** `save()` becomes one call; the "saved, but credential not updated" notice disappears
   for validation errors (they are now reported before anything is stored). TS validation stays for
   fast feedback.
5. **Tests.** Service tests: invalid secret leaves the profile unchanged; credential-store failure
   leaves profile and secret as before; update with `Keep` preserves the reference; revocation
   happens once. Playwright mock updated.
6. **Compatibility.** Same `credential_ref` format (`reference_for`), same Credential Manager entries,
   same table. Old commands remain until a later cleanup.
7. **Acceptance.** No sequence of failures leaves a new profile with a rejected credential; the form
   shows one error; existing profiles and credentials from v0.1.0/v0.2.0 still load and connect.

### M2 — Extract the monitor pipeline and the revocation policy (F3, F4)

1. **Problem.** The most intricate runtime logic sits in Tauri command files with almost no tests, and
   one DB call runs synchronously on an async worker.
2. **Files.** `commands/monitor.rs`, new `monitoring/{mod,pipeline}.rs`, `commands/servers.rs`,
   `servers/service.rs`, `state.rs`.
3. **Rust.** Move `alerts_for_sample`, `note_gap`, `close_alerts`, `record_history` and the forwarder
   loop into `monitoring::pipeline`, driven through a small `EventSink` trait (Tauri `Channel` in
   production, a `Vec` in tests). Keep ordering exactly: gap, alerts, send, record, then close. Run
   alert DB work inside `spawn_blocking` like history. Move `validate_interval` and `MAX_MONITORS`
   next to it. Add a pure `servers::service::change_effects(before, after) -> ChangeEffects`
   (`stop_monitor`, `close_terminals`) used by `update_server`; the credential wrappers already call
   `revoke_server` and should use the same type.
4. **Frontend.** None.
5. **Tests.** Pipeline: gap resets streaks but keeps firing alerts; superseded monitor does not close
   the newer monitor's alerts; deleted server drops alerts silently; sink failure stops the monitor;
   history failure never interrupts monitoring and logs once. Policy: rename keeps terminals,
   host/port/user/auth change revokes.
6. **Compatibility.** Behavior-preserving refactor; event JSON unchanged; lock order (DB then
   registry) must be preserved and asserted in comments and tests.
7. **Acceptance.** All existing alert, history and monitor tests pass unchanged; new pipeline tests
   run without a Tauri `AppHandle`; `commands/monitor.rs` is under about 60 lines.

### M3 — Structured connection failure kind (F5)

1. **Problem.** Terminal, Docker and log failures are free-text `connection` errors; the UI cannot tell
   an authentication failure from a network error, so terminal auth failure is labelled generically.
2. **Files.** `error.rs`, `ssh/client.rs` (`explain`), `ssh/terminal.rs`, `ssh/docker/{mod,logs}.rs`,
   `commands/{terminal,docker}.rs`, `types/servers.ts`, `services/ipc.ts`,
   `services/connectionStatus.ts`, terminal and Docker pages.
3. **Rust.** Add optional `kind` to `AppError` reusing the existing `ConnectionTestOutcome` vocabulary
   (`host_key_unknown`, `host_key_changed`, `auth_failed`, `no_credential`, `unreachable`, `timeout`,
   `error`). The SSH layer already computes the outcome; carry it instead of dropping it. Messages stay
   exactly as written today (never echo remote text or secrets).
4. **Frontend.** `TerminalSessionState.error` gains `cause`; `deriveConnectionStatus` maps
   `cause === "auth_failed"` to the same status the monitor uses. No new rules are decided in TS.
5. **Tests.** Rust table test failure to kind; Vitest status precedence unchanged for all existing
   cases plus terminal auth failure; Docker error path unchanged.
6. **Compatibility.** Field is optional and skipped when absent, so older frontends ignore it.
7. **Acceptance.** Terminal and monitor show the same label for the same failure; no message text
   changed; no secret or remote output appears in any error.

### M4 — Validation conformance and single-source limits (F6)

1. **Problem.** Limits and validators are duplicated by hand and can drift (leading-zero IPv4 is a
   likely current example).
2. **Files.** New `src-tauri/src/limits.rs`; new fixture `apps/desktop/test-fixtures/validation-cases.json`;
   `services/serverValidation.ts`, `alertsState.ts`, `historyState.ts` tests; optionally a read-only
   `get_limits` command (permission added in all three places).
3. **Rust.** Collect shared constants (name/username/description/secret sizes, alert limits, retention,
   range, interval, tail options) in `limits.rs`; model modules re-export them. Add a Rust test that
   loads the fixture. Optionally expose the constants via `get_limits` so TS stops re-declaring them.
4. **Frontend.** Vitest runs the same fixture against `validateServerForm`, `validateRuleForm`,
   `parseRetention`. Fix any mismatch the fixture reveals (decide which side is right; Rust wins for
   security). If `get_limits` is added, load limits once at startup with the current constants as
   fallback. Optionally let Rust own the default poll interval (`interval_secs` optional).
5. **Tests.** The shared corpus is the test. Include IPv4 leading zeros, IPv4-mapped IPv6, 63/64-char
   labels, 253/254-char hosts, control characters, multi-byte names and secrets at 2560/2561 bytes.
6. **Compatibility.** No behavior change on the Rust side; TS may become stricter to match Rust.
7. **Acceptance.** Both suites pass on one corpus; adding a case to the corpus exercises both sides.

### M5 — IPC golden contracts (F8)

1. **Problem.** DTOs are mirrored by hand in `types/*.ts`.
2. **Files.** `src-tauri/tests/ipc_contract.rs`, `apps/desktop/test-fixtures/ipc/*.json`, a Vitest
   `contract.test.ts`.
3. **Rust.** Serialize representative `Metrics`, each `MonitorEvent`, `AlertEvent`, `ActiveAlert`,
   `HistoryRange`, `AppError`, `ConnectionTestResult`, `DockerResult`, `LogsResult` and compare with the
   goldens.
4. **Frontend.** Type-check goldens with `satisfies` against `types/*.ts`; fail on missing or extra keys.
5. **Tests.** The contract tests themselves; regeneration documented in `docs/development/setup.md`.
6. **Compatibility.** Test-only; no runtime change.
7. **Acceptance.** Renaming a Rust field or changing a serde tag fails a test on the TS side.

### M6 — Optional polish

- **Atomic recommended alert rules.** `AlertsPage` creates three presets with three sequential calls.
  An `apply_recommended_alert_rules` command would make it all-or-nothing. Presets and wording can stay
  in TS; the command takes no input. Skip if rules are not commonly created this way.
- **Alert staleness from Rust.** `isAlertStale` is a pure function of monitor state and is fine. Only
  revisit if alerts ever survive restarts.
- **Readiness reason from Rust.** Add `ready`/`blocker_kind` to a new readiness command so
  `serverReadiness.ts` only supplies wording. Low value; Rust already enforces.

## 8. What should explicitly stay in TypeScript

Component and provider state, theme, chart geometry and gap breaks, colour bands (`usageTone`),
fleet averages and number/time formatting, Docker sort/filter/summary, log level *guess* and
filtering, connection-test labels and tones, the live 60-sample sparkline buffer, input chunking and
base64 decoding for the terminal, demo data, and wording of readiness and stale-alert messages. None of
these decide what is allowed, what is stored, or what is an incident.

`deriveConnectionStatus` also stays: it merges the monitor stream and the terminal session, both of
which the UI already holds, and a reload ends both (terminals are closed on page load; a monitor stops
when its channel is dropped), so there is no server-side snapshot worth reading.

## 9. Risks

| Risk | Mitigation |
| --- | --- |
| F1 is based on reading Tauri source, not on a run. | M0 step 1 reproduces it before changing anything; if History works, the fix is still needed for consistency but severity drops. |
| Changing the capability file looks like a permission change. | Only three explicit grants matching existing handlers; reviewed by the M0 consistency test; no `core:` or plugin additions. |
| `e2e/tauriMock.ts` can drift from real commands and hides ACL errors. | Update the mock with each new command; add a real-IPC smoke check (Section 6). |
| M2 touches lock ordering and async/blocking boundaries. | Behavior-preserving; keep DB-then-registry order; keep existing tests unchanged; add pipeline tests first. |
| M1 changes how credentials are written. | Reuse the existing compensation protocol and `reference_for`; keep old commands; test with `MemoryStore` failure injection; manual check against real Credential Manager. |
| Single global DB mutex (A-02 in the audit) is now touched on every sample for alerts and history. | Out of scope; M2's `spawn_blocking` for alerts reduces runtime blocking; revisit only if profiling shows contention. |
| Over-extracting into new modules or crates. | No new crate; only one new module (`monitoring`) and one new file (`limits.rs`). |
| Nothing in this plan has been validated on real servers (see the v0.2.0 readiness audit). | Run the existing manual beta checklist after M0-M3. |

## 10. Final recommendation

1. **Do not migrate or rewrite anything wholesale.** The backend is already fully in Rust and is the
   authority for validation, trust, credentials, alerts, history, Docker and persistence. The
   TypeScript that remains is presentation, view-model folding and UX-only validation.
2. **Do M0 now**, before the v0.2.0 beta ships. If the audit's reading is right, History and the
   retention setting are broken in the installed app, and the E2E suite cannot see it.
3. **Then M1 and M2** (atomic save, pipeline extraction). They remove the only real orchestration in
   the UI and the least-tested business logic in the command layer.
4. **M3-M5 are hardening** and can follow the beta: consistent failure labels, a shared validation
   corpus, and golden IPC contracts.
5. **Do not touch** SSH host-key verification, SQLite migrations, the app identifier, credential
   references, the Tauri capability model, or any UI presentation code.
